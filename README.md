# aws-terraform-dojo

AWS Terraformを**生成AIに書かせず、自分の手で実装する**ための学習用リポジトリ（道場）です。

## 道場のコンセプト

生成AIにコードを書かせれば、動くTerraformはすぐに手に入ります。しかし「なぜこのリソース構成が必要なのか」「なぜこの書き方をするのか」という設計判断の力は、実際に手を動かして詰まった経験からしか身につきません。

このリポジトリでは、Claude Codeに以下の3つだけを担当させ、**Terraformの実装コード（`.tf`ファイルの中身）は一切書かせません**。

1. リポジトリ構造とドキュメントの整備
2. 各お題の「仕様書」（SPEC.md）の作成
3. 完成後の受入テスト結果に対するレビュー支援

仕様書を読み、手を動かし、詰まり、調べ、直す——このサイクルを踏むことが道場の目的です。

## 難易度の示し方: スコア×カテゴリ

お題（kata）フォルダはかつて「番号帯で段位（白帯〜黒帯）を表す」方式（`001`〜`099`=白帯、等）を採用していましたが、
現在は廃止しています。VPC自作のような特定要素がスコアを跳ね上げるケースで帯の閾値調整が煩雑になったこと、
「黒帯」という1つのラベルに性質の異なる複雑さ（ネットワーク設計系・組織委譲系など）が混在し説明力が薄れたことが理由です。

現在は `katas/` 直下に段位フォルダなしで、単純な連番（`001`, `002`, `003`, ...）のみを振ります。番号は作成順であり、難易度を表しません。
難易度は各SPEC.mdの「難易度」セクションに記載する**スコア**と**カテゴリ**の2軸で示します。

- **スコア**: `docs/difficulty-score.md` の計算式（難易度スコア = S×2 + R + 深さ×3 + エッジ数×1 + T×1.5）で機械的に算出する数値。RPGのモンスターレベル表示のように、そのkataに着手する前の「身構える目安」として使う
- **カテゴリ**: 複雑さの性質を示すタグ（例: ネットワーク設計系、組織委譲系、配線密度系、妥協点設計系）。1つのkataに複数付けてよい。詳細は `docs/difficulty-score.md` を参照

「特別枠」という区分自体は残していますが、位置づけが変わりました。難易度の高さではなく、**個人の検証環境で再現できるかどうか**のみを基準にした「採用可否」の判定枠です。詳細は `docs/special-tier.md` を参照してください。

## リポジトリ構成

```
aws-terraform-dojo/
├── README.md                  # このファイル
├── katas/                     # お題（型）。段位フォルダなし、単純な連番でフラットに並べる
│   ├── 001-provider-init/
│   ├── 002-ec2-only/
│   ├── 003-security-group/
│   ├── 004-user-data-nginx/
│   ├── 005-outputs/
│   ├── 006-restrict-source-ip/
│   ├── 007-bastion-sg-reference/
│   ├── 008-vpc-subnets/
│   ├── 009-nat-gateway/
│   └── 010-rds-private-connect/   # 特別枠（個人のAWSアカウントで再現可能）
├── templates/
│   └── SPEC_TEMPLATE.md       # 仕様書のテンプレート
└── docs/
    ├── difficulty-score.md    # 難易度スコア・カテゴリの算出基準
    ├── special-tier.md        # 特別枠（採用可否）の定義
    └── review-checklist.md    # レビュー観点まとめ
```

`006-restrict-source-ip` から `010-rds-private-connect` までは、「RDSへの比較的セキュアな接続」をゴールとした一連の誘導問題です。1問ごとに新しい概念を1つずつ積み上げ、`006`(送信元IP絞り込み・スコア11) → `007`(セキュリティグループ同士の参照・スコア18) → `008`(VPC/サブネット自作・スコア43) → `009`(NATゲートウェイ・スコア56) → `010`(RDSへの接続・スコア80、特別枠)と進みます。`008`以降で算出した難易度スコアが直感的な想定より大きく跳ね上がっているのは、VPCを自作した時点で以降のほぼ全リソースがVPCを参照する「配線のハブ」になるためです（理由は各SPEC.mdの「難易度」節を参照）。

各お題ディレクトリの構成は共通です。

```
katas/<お題番号>-<お題名>/
├── SPEC.md         # 仕様書（要件・制約・受入テスト・難易度スコアを定義）
├── terraform/      # ここに自分の手でTerraformコードを実装する（空、.gitkeepのみ）
└── tests/
    └── acceptance.sh   # 受入テストの雛形
```

## お題の進め方

1. `katas/<お題番号>-<お題名>/SPEC.md` を読む
2. `SPEC.md`の「要件（Must）」「制約（禁止事項）」を理解した上で、`terraform/` 配下に**自分の手で**Terraformコードを実装する（生成AIによるコード生成は使わない）
3. `terraform plan` / `terraform apply` の後、`tests/acceptance.sh` を実行して自己採点する
4. 実行結果を持ってClaude Codeにレビューを依頼する

`katas/` 配下のkataは、1つ前のkataの `terraform/` をコピーして発展させる構成になっています。`001-provider-init` から番号順に進めてください。

## レビュー依頼時のプロンプト例

```
katas/002-ec2-only の受入テストを実施しました。
以下が terraform plan の出力と acceptance.sh の実行結果です。
SPEC.md のMust要件を満たしているか判定してください。

--- terraform plan の出力 ---
(ここに貼る)

--- acceptance.sh の実行結果 ---
(ここに貼る)
```

Claude Codeは実装コードを書き直すのではなく、`docs/review-checklist.md` の観点に沿って、SPEC.mdの要件に対する充足性判定と改善のためのフィードバックのみを行います。

## 新しいお題を追加する場合

`templates/SPEC_TEMPLATE.md` をコピーして、`katas/<お題番号>-<お題名>/SPEC.md` として作成してください。
番号は段位を表さない単純な連番です。既存の最大値の次の番号を3桁ゼロ埋めで付けてください（`find katas -maxdepth 1 -type d` で確認できます）。
難易度は `docs/difficulty-score.md` の計算式でスコアを算出し、該当するカテゴリとあわせてSPEC.mdの「難易度」セクションに明記してください。
そのkataを道場に採用してよいか（個人の検証環境で再現できるか）は `docs/special-tier.md` を参照して判断してください。
