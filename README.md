# aws-terraform-dojo

AWS Terraformを**生成AIに書かせず、自分の手で実装する**ための学習用リポジトリ（道場）です。

## 道場のコンセプト

生成AIにコードを書かせれば、動くTerraformはすぐに手に入ります。しかし「なぜこのリソース構成が必要なのか」「なぜこの書き方をするのか」という設計判断の力は、実際に手を動かして詰まった経験からしか身につきません。

このリポジトリでは、Claude Codeに以下の3つだけを担当させ、**Terraformの実装コード（`.tf`ファイルの中身）は一切書かせません**。

1. リポジトリ構造とドキュメントの整備
2. 各お題の「仕様書」（SPEC.md）の作成
3. 完成後の受入テスト結果に対するレビュー支援

仕様書を読み、手を動かし、詰まり、調べ、直す——このサイクルを踏むことが道場の目的です。

## 段位制度

お題（kata）フォルダは段位ごとにネストせず、`katas/` 直下に3桁の数字プレフィックスの「番号帯」でフラットに並べます。
番号帯が段位を表し、同じ番号帯の中で連番（`001`, `002`, ...）を振ります。アルファベット順ソートがそのまま段位順・お題順になります。

| 段位 | 番号帯 | テーマ | 内容 |
|---|---|---|---|
| 白帯 | 001〜099 | 単一リソース中心 | EC2 + SGなど、基本的なリソースを単体で組む。1kata=1新規概念 |
| 黄帯 | 101〜199 | 複数リソースの依存関係 | ALB + ASG + 複数AZなど、リソース間の依存・参照を扱う |
| 茶帯 | 201〜299 | モジュール化・状態管理 | モジュール分割、tfvars分離、リモートステート |
| 黒帯 | 301〜399 | 組織レベルの設計 | マルチアカウント、IAMロール委譲、コスト制約付き設計 |
| 特別枠 | 901〜999 | 閉域網・専用ツールとの役割分担 | プライベートサブネット越しの疎通、Databricks/Bedrock AgentCoreのようにTerraformの外側に専用CLI/SDKが存在するお題など。上記の帯の枠組みでは難易度を測れない、または前提条件が異なるもの |

各お題の難易度（どの番号帯に置くか）は感覚ではなく、`docs/difficulty-score.md` の計算式で算出したスコアに基づいて決定します。
特別枠の詳細（該当条件・SPEC.mdに必須の項目）は `docs/special-tier.md` を参照してください。

## リポジトリ構成

```
aws-terraform-dojo/
├── README.md                  # このファイル
├── katas/                     # お題（型）。段位フォルダなし、番号帯でフラットに並べる
│   ├── 001-provider-init/         # 白帯
│   ├── 002-ec2-only/
│   ├── 003-security-group/
│   ├── 004-user-data-nginx/
│   └── 005-outputs/
├── templates/
│   └── SPEC_TEMPLATE.md       # 仕様書のテンプレート
└── docs/
    ├── difficulty-score.md    # 難易度スコアの算出基準
    ├── special-tier.md        # 特別枠の定義
    └── review-checklist.md    # レビュー観点まとめ
```

黄帯（101〜）・茶帯（201〜）・黒帯（301〜）・特別枠（901〜）は、現時点ではまだお題がありません。今後、`docs/difficulty-score.md` のスコアに基づいて追加していきます。

各お題ディレクトリの構成は共通です。

```
katas/<お題番号>-<お題名>/
├── SPEC.md         # 仕様書（要件・制約・受入テスト・難易度スコアを定義）
├── terraform/      # ここに自分の手でTerraformコードを実装する（空、.gitkeepのみ）
└── tests/
    └── acceptance.sh   # 受入テストの雛形
```

## お題の進め方

1. `katas/<お題番号>-<お題名>/SPEC.md` を読む
2. `SPEC.md`の「要件（Must）」「制約（禁止事項）」を理解した上で、`terraform/` 配下に**自分の手で**Terraformコードを実装する（生成AIによるコード生成は使わない）
3. `terraform plan` / `terraform apply` の後、`tests/acceptance.sh` を実行して自己採点する
4. 実行結果を持ってClaude Codeにレビューを依頼する

白帯（001〜099）は、1つ前のkataの `terraform/` をコピーして発展させる構成になっています。`001-provider-init` から順番に進めてください。

## レビュー依頼時のプロンプト例

```
katas/002-ec2-only の受入テストを実施しました。
以下が terraform plan の出力と acceptance.sh の実行結果です。
SPEC.md のMust要件を満たしているか判定してください。

--- terraform plan の出力 ---
(ここに貼る)

--- acceptance.sh の実行結果 ---
(ここに貼る)
```

Claude Codeは実装コードを書き直すのではなく、`docs/review-checklist.md` の観点に沿って、SPEC.mdの要件に対する充足性判定と改善のためのフィードバックのみを行います。

## 新しいお題を追加する場合

`templates/SPEC_TEMPLATE.md` をコピーして、`katas/<お題番号>-<お題名>/SPEC.md` として作成してください。
番号は割り当てる段位の番号帯（白帯001〜099 / 黄帯101〜199 / 茶帯201〜299 / 黒帯301〜399 / 特別枠901〜999）の中で連番を、3桁ゼロ埋めで付けてください。
どの番号帯に置くかは、`docs/difficulty-score.md` の計算式でスコアを算出した上で判断してください。
