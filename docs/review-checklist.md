# レビューチェックリスト

Claude Codeが受入テスト結果・`terraform plan`出力のレビューを依頼された際に確認する観点。
このチェックリストは、Claude Code自身がレビュー時に参照するほか、受講者が自己採点する際の参考にもなる。

## 1. Must要件の充足性

- [ ] SPEC.mdのMust要件を一つずつ突き合わせ、満たしているかを判定する
- [ ] `acceptance.sh`の実行結果（PASS/FAIL）とMust要件の対応関係を確認する
- [ ] `plan`出力から、実際に作成されようとしているリソースがMust要件と矛盾していないか確認する（例: セキュリティグループの送信元、ポート番号、インスタンスタイプなど）

## 2. 制約（禁止事項）への抵触

- [ ] `0.0.0.0/0` や `::/0` など、過剰に広い送信元・宛先が使われていないか
- [ ] IAMポリシーに `*` を使った過剰な権限付与がないか
- [ ] SPEC.mdで許可された範囲外のAWSサービスを使っていないか

## 3. テストの妥当性

- [ ] `acceptance.sh`のテストが、表面的なPASSで満足せず「本当にMust要件を検証できているか」
- [ ] 「許可された経路からの成功」と「許可されていない経路からの失敗」の両方が検証されているか
- [ ] タイムアウトやリトライの設定が、誤検知（flakyな判定）を招いていないか

## 4. 推奨（Should）への準拠

- [ ] 命名規則・タグ付けが一貫しているか
- [ ] 変数化・ハードコード回避など、保守性への配慮があるか

※ Shouldは複数の正解が許容される領域のため、未準拠でも即座にNG判定にはしない。改善提案として伝える。

## 5. フィードバックの伝え方

- Must要件の判定結果（合格/不合格）を要件ごとに明確に伝える
- 不合格の場合は、SPEC.mdのどの要件に対してどう不足しているかを具体的に指摘する
- **実装コード自体を書き直して提示しない**（道場の趣旨に反するため）。修正の方向性や調べるべきキーワードの提示にとどめる

## 6. スコープ外の指摘

- SPEC.mdの「スコープ外」に該当する提案は、参考情報として触れる程度にし、今回のお題の合否判定には含めない

## 7. SPEC作成時のセルフチェック（Must ↔ acceptance.sh対応）

新しいSPEC.mdを書いた、または既存のSPEC.mdを修正した際に、公開前（受講者に渡す前）に必ず確認する。この観点が漏れると、「Mustに書いたが実際には検証できない項目」が紛れ込み、`tests/acceptance.sh`による自己採点が信頼できなくなる（[[difficulty-score]]のT=受入テストの検証項目数の前提が崩れる原因にもなる）。

- [ ] Mustの各項目について、`tests/acceptance.sh`のどの行（またはどのAWS API呼び出し）が対応するかを1つずつ指差し確認できるか。対応する行がない場合、その項目はMustから外す（Should化するか、背景・目的の説明文に理由として記載するに留める）
- [ ] 「〇〇ブロックを書かないこと」「△△という書き方をしないこと」のような、コードの書き方・実装の形そのものに関する制約がMustに紛れていないか。`terraform validate`は文法チェックしかできず、AWS上に何も作られない段階（例: providerのみのkata）ではそもそも問い合わせる先の状態が存在しないため、原理的に検証不可能。この種の申し合わせはShouldに置く
- [ ] 各テスト項目が「意図的に要件を満たさない実装」を弾けるか（vacuous pass対策）。例えば「禁止ポートの許可ルールが0件であること」だけを見る実装だと、必須ポートすら1つも開放していない実装が誤ってPASSしてしまう。「許可すべきものが存在する」ことと「許可してはいけないものが存在しない」ことの両方を確認する
- [ ] Mustの中に、内容が重複・言い換えに過ぎない項目がないか（例:「EC2を起動する」と「applyが成功しrunning状態になる」を別々のMustとして書いていないかなど）。重複はテストとの対応関係を追いにくくするので1項目にまとめる
- [ ] 前のkataから引き継ぐMust（「引き続き維持する」等）についても、当該kataの`tests/acceptance.sh`で実際に再検証しているか。「前のkataで検証済みだから今回は省略してよい」という判断をしていないか
- [ ] 制約（禁止事項）セクションに書いた内容は、Mustのような機械的な自動採点ではなく、`terraform plan`出力の目視確認などレビュー時の人間による判断に委ねる前提であることを踏まえているか。Mustと役割を混同していないか
