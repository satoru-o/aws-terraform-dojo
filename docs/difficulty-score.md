# 難易度スコア算出基準

新規お題（kata）の難易度を「作成者の感覚」ではなく、機械的に再現可能な指標で決めるための基準。
段位（帯）を割り当てる際、また既存お題の難易度が妥当かを後から検証する際に、必ずこの基準でスコアを算出すること。

## 前提（重要）

難易度スコアは、**そのkataを解くための最小十分な構成（模範解答）**を基準に算出する。
受講者が実際に提出した実装がどれだけ複雑化したか・リソース数を水増ししたかとは無関係である。

例: 「同じ役割のEC2インスタンスを無意味に数珠つなぎにする」「不要なモジュール分割をする」といった実装をした受講者がいても、
それによってそのkataの難易度スコアが変わることはない。あくまで「これ以上削れない最小構成なら何点か」で評価する。

そのため、SPEC.mdを書く担当者（Claude Code）は、要件を満たす最小構成を頭の中で（または実際に）組み立てた上でスコアを算出する。

## スコア計算式

```
難易度スコア = S×2 + R + 深さ×3 + エッジ数×1 + T×1.5
```

| 記号 | 意味 | 数え方 |
|---|---|---|
| S | 使用するAWSサービスの種類数 | 模範解答が使うAWSサービスの異なる分類の数。迷った場合はAWSマネジメントコンソールの左ナビゲーションの分類を基準にする（例: EC2、VPC、S3、RDS、IAM、Glue、Redshift）。EC2インスタンスに付随するセキュリティグループなど、同一サービスのネットワーキング機能とみなせるものは同一サービスとして数え、別カウントしない |
| R | Terraformリソースブロックの個数 | 模範解答の `resource "..." "..." { ... }` ブロックの総数。`data` ブロック（情報取得のみで新規リソースを作らないもの）はカウントしない |
| 深さ | リソース依存グラフにおける最長パスの長さ | リソースAがBを参照し、BがCを参照する場合、深さ2。参照が一切なければ深さ0。`data`ブロック経由の参照は数えない（`resource`同士の参照のみ） |
| エッジ数 | リソース間の参照（矢印）の総本数 | `resource`ブロックが他の`resource`ブロックの属性・IDを参照している箇所の総数（`for_each`や`count`で複数生成される場合も、参照の種類ごとに1本と数える。同一参照を繰り返すループはこの限りではないため、迷う場合はSPEC作成時に想定される最小構成での本数を使う） |
| T | 受入テストの検証項目数 | `tests/acceptance.sh`（または受入テスト表）に記載する検証項目の数 |

## 段位とスコアレンジ

| 段位 | 番号帯 | スコアレンジ |
|---|---|---|
| 白帯 | 001〜099 | 〜12 |
| 黄帯 | 101〜199 | 13〜19 |
| 茶帯 | 201〜299 | 20〜32 |
| 黒帯 | 301〜399 | 33〜 |
| 特別枠 | 901〜999 | 上記の枠組みでは測れない、または前提条件が異なるもの（[[special-tier]] 参照） |

## 運用ルール

- 新規kataを追加する際は、必ずこの式でスコアを算出し、`SPEC.md` の末尾（「スコープ外」の後）に以下の形式で明記する。

  ```
  ## 難易度スコア

  XX点（S=?, R=?, 深さ=?, エッジ=?, T=?）
  ```

- 算出したスコアが、割り当てようとしている段位のレンジから外れる場合は、以下のいずれかで調整する。
  - 要件（Must）を増減してスコアがレンジに収まるよう調整する
  - 番号帯（段位）を、算出されたスコアに合ったものに変更する
- スコアだけで機械的に決め切れない場合（例: 概念的には簡単だが調査に時間がかかる、など）は、算出したスコアと実際の体感難易度の両方をSPEC.md作成時のメモとして残し、判断根拠を明確にする。
- 既存kataのスコアが妥当か疑わしくなった場合は、このドキュメントの式で再計算し、レンジ外であればお題またはレンジ設定の見直しを検討する。
