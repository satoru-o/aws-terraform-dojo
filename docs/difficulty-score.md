# 難易度スコア算出基準

新規お題（kata）の難易度を「作成者の感覚」ではなく、機械的に再現可能な指標で決めるための基準。
新規kataを作成する際、また既存お題の難易度が妥当かを後から検証する際に、必ずこの基準でスコアを算出すること。

道場はかつて、算出したスコアを3桁の番号帯（白帯/黄帯/茶帯/黒帯）に変換し、kataのフォルダ番号でその段位を表す運用をしていた。
しかしVPC自作のような特定要素がスコアを跳ね上げるケースがあり、帯の閾値をその都度調整する運用が煩雑になったこと、また「黒帯」という
1つのラベルの中に性質の異なる複雑さ（ネットワーク設計系・組織委譲系など）が混在し説明力が薄れたことから、帯制度は廃止した。
現在はkataフォルダを単純な連番（`001`, `002`, `003`...）で管理し、難易度は「スコア」と「カテゴリ」の2軸で表現する（後述）。

## 前提（重要）

難易度スコアは、**そのkataを解くための最小十分な構成（模範解答）**を基準に算出する。
受講者が実際に提出した実装がどれだけ複雑化したか・リソース数を水増ししたかとは無関係である。

例: 「同じ役割のEC2インスタンスを無意味に数珠つなぎにする」「不要なモジュール分割をする」といった実装をした受講者がいても、
それによってそのkataの難易度スコアが変わることはない。あくまで「これ以上削れない最小構成なら何点か」で評価する。

そのため、SPEC.mdを書く担当者（Claude Code）は、要件を満たす最小構成を頭の中で（または実際に）組み立てた上でスコアを算出する。

## スコア計算式

```
難易度スコア = S×2 + R + 深さ×3 + エッジ数×1 + T×1.5
```

| 記号 | 意味 | 数え方 |
|---|---|---|
| S | 使用するAWSサービスの種類数 | 模範解答が使うAWSサービスの異なる分類の数。迷った場合はAWSマネジメントコンソールの左ナビゲーションの分類を基準にする（例: EC2、VPC、S3、RDS、IAM、Glue、Redshift）。EC2インスタンスに付随するセキュリティグループなど、同一サービスのネットワーキング機能とみなせるものは同一サービスとして数え、別カウントしない |
| R | Terraformリソースブロックの個数 | 模範解答の `resource "..." "..." { ... }` ブロックの総数。`data` ブロック（情報取得のみで新規リソースを作らないもの）はカウントしない |
| 深さ | リソース依存グラフにおける最長パスの長さ | リソースAがBを参照し、BがCを参照する場合、深さ2。参照が一切なければ深さ0。`data`ブロック経由の参照は数えない（`resource`同士の参照のみ） |
| エッジ数 | リソース間の参照（矢印）の総本数 | `resource`ブロックが他の`resource`ブロックの属性・IDを参照している箇所の総数（`for_each`や`count`で複数生成される場合も、参照の種類ごとに1本と数える。同一参照を繰り返すループはこの限りではないため、迷う場合はSPEC作成時に想定される最小構成での本数を使う） |
| T | 受入テストの検証項目数 | `tests/acceptance.sh`（または受入テスト表）に記載する検証項目の数 |

## カテゴリ

スコアだけでは「何が難しいのか」という複雑さの性質までは伝わらない。そこで、スコアと併せて**カテゴリ**（複雑さの性質を示すタグ）を付与する。
1つのkataに複数のカテゴリを付けてよい。初期カテゴリは以下の4つ。

| カテゴリ | 説明 |
|---|---|
| ネットワーク設計系 | VPC・サブネット・ルートテーブル・NATゲートウェイなど、単一アカウント内でリソース間の配線が複雑化するタイプ |
| 組織委譲系 | マルチアカウント、クロスアカウントIAM、権限委譲など、組織・ガバナンスレベルの複雑さが主因のタイプ |
| 配線密度系 | サービス数・深さ自体は少ないが、1対多の関係（ファンアウト等）でエッジ数だけが積み上がるタイプ。深さ×3・エッジ数×1の合計がRの寄与を上回る場合の目安になる |
| 妥協点設計系 | SaaS外部連携やエディション制約などにより技術的に理想的な解が存在せず、リスク低減の落としどころを自分で判断する必要があるタイプ |

該当するカテゴリがなければ「カテゴリ: なし」と明記する。上記4つで表現しきれない性質のkataが今後出てきた場合は、
このカテゴリ一覧に新しいカテゴリを追加してよい（追加時はこの表に説明を書き足すこと）。

## 採用可否について

スコア・カテゴリはあくまで難易度の「表示」であり、そのkataを道場のラインナップに採用するかどうかの判定基準ではない。
採用可否（個人の検証環境で再現できるか）は `docs/special-tier.md` を参照すること。

## 運用ルール

- 新規kataを追加する際は、必ずこの式でスコアを算出し、`SPEC.md` の末尾（「スコープ外」の後）に以下の形式で明記する。

  ```
  ## 難易度

  スコア: XX（S=?, R=?, 深さ=?, エッジ=?, T=?）
  カテゴリ: カテゴリ名（複数可、なければ「なし」）
  ```

- カテゴリの判断に迷う場合は、深さ×3とエッジ数×1の合計がRの寄与を上回っていれば「配線密度系」、VPC/サブネット/ルーティング関連のリソードが主因なら「ネットワーク設計系」、といったように「スコアのどの項がなぜ大きいか」を根拠にする。
- スコアだけで機械的に決め切れない場合（例: 概念的には簡単だが調査に時間がかかる、など）は、算出したスコアと実際の体感難易度の両方をSPEC.md作成時のメモとして残し、判断根拠を明確にする。
- 既存kataのスコアが妥当か疑わしくなった場合は、このドキュメントの式で再計算し、SPEC.mdの記載を更新する。
- フォルダ番号は段位を表さない単純な連番（`001`, `002`, `003`...）とする。新規kataの番号は既存の最大値の次を割り当てる。
